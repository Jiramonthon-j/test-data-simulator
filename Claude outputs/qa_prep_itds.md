# เตรียมคำถาม-คำตอบ สอบสหกิจศึกษา
## Intelligent Test Data Simulator

เอกสารนี้รวบรวมคำถามที่กรรมการมีโอกาสถามสูง โดยอ้างอิงจากเนื้อหาจริงในสไลด์ (33 หน้า) แบ่งเป็น 2 กลุ่ม: **กลุ่มต้องตอบได้คล่องที่สุด** (เพราะย้ายรายละเอียดไปเก็บไว้ในภาคผนวก ไม่ได้พูดเต็มในเนื้อหาหลัก) และ **กลุ่มคำถามทั่วไป** ตามลำดับหัวข้อของสไลด์

---

## ตัวเลขที่ต้องจำขึ้นใจ (กรรมการชอบถามย้อนตัวเลข)

- Condition Match ขั้นต่ำ **70%** และ Reliability ขั้นต่ำ **90%** — ต้องผ่านพร้อมกันทั้งสองค่า
- จำนวนแถวสูงสุดต่อคำขอ **300 แถว**
- Retry เมื่อ Gemini API ไม่ตอบสนอง สูงสุด **6 ครั้ง**
- ล็อกบัญชีชั่วคราว **60 วินาที** หลังกรอกรหัสผ่านผิด **3 ครั้งติดกัน**
- Session หมดอายุอัตโนมัติเมื่อไม่ใช้งานเกิน **10 นาที**
- ระยะเวลาโครงงาน **14 สัปดาห์** (มิ.ย.–ก.ย. 2569)
- โมเดลที่ใช้: **Gemini 3.6 Flash**

## กลุ่ม A: ต้องตอบได้คล่องที่สุด (เนื้อหาอยู่ในภาคผนวก)

### 1. รู้ได้อย่างไรว่าข้อมูลที่ AI สร้างเชื่อถือได้ ไม่ใช่ AI มั่วขึ้นมาเอง?

ระบบตรวจสอบคุณภาพข้อมูล 2 ชั้นก่อนอนุญาตให้บันทึก:

1. **ตรวจเชิงโครงสร้างด้วยโค้ด** (ไม่ใช้ AI) — จำนวนแถวตรงตามที่ขอหรือไม่ คอลัมน์ขาด/เกินหรือไม่ มีค่าว่างหรือไม่ ถ้าโครงสร้างมีปัญหา คะแนนรวมไม่ผ่านทันที เพื่อกันไม่ให้คะแนนหลอกสูงเกินจริง
2. **ให้ Gemini ประเมินตัวเอง (Self-check)** เทียบข้อมูลที่สร้างกับเงื่อนไขที่ผู้ใช้ตั้งไว้

รวมคะแนนสองส่วนแล้วต้องผ่านเกณฑ์ทั้ง Condition Match ≥70% และ Reliability ≥90% พร้อมกัน ถ้าค่าใดค่าหนึ่งต่ำกว่าเกณฑ์ ระบบแจ้งเตือนให้ตรวจสอบก่อนตัดสินใจ Commit — สรุปคือไม่ปล่อยให้ AI ตัดสินคุณภาพของตัวเองฝ่ายเดียว มีโค้ดคอยควบคุมอีกชั้น

### 2. ทำไมต้องมี Rule-Based Mode ในเมื่อมี Legacy Mode อยู่แล้ว?

เพราะ Legacy Mode ให้ AI ตัดสินใจทุกแถว — ถ้าขอ 100 แถว ก็ต้องพึ่ง AI 100 ครั้ง (หรือใน prompt เดียวที่ใหญ่มาก) กิน Token สูงและผลลัพธ์อาจไม่สม่ำเสมอ Rule-Based Mode แก้ปัญหานี้ด้วยการแยกงานเป็น 2 เฟส:

- **เฟส 1 (Compile Rules):** เรียก Gemini API **ครั้งเดียว** ต่อการสร้างข้อมูล 1 ชุด เพื่อแปลเงื่อนไข + DDL ให้เป็นกฎการสร้างข้อมูล (Generator Rules) รูปแบบ JSON ต่อคอลัมน์
- **เฟส 2 (Generate Rows):** สร้างข้อมูลทุกแถวด้วยโค้ดล้วนตามกฎที่ได้ ไม่เรียก AI เพิ่มอีกเลย

ผลคือประหยัด Token ได้มาก และผลลัพธ์สม่ำเสมอกว่า เพราะไม่ได้ให้ AI สุ่มตัดสินใจทีละแถว (ปัจจุบันยังเป็นสถานะ Beta)

### 3. ทำไมเลือก Gemini ไม่ใช้ ChatGPT หรือโมเดลอื่น?

สองเหตุผลหลัก: (1) Gemini อ่าน/เข้าใจภาษาไทยแม่นยำกว่าโมเดลอื่นที่เปรียบเทียบ ทำให้ตีความเงื่อนไขและโครงสร้างข้อมูลภาษาไทยได้ถูกต้องกว่า (2) มี API Key ใช้งานได้ฟรีภายใน Rate Limit ที่กำหนด ไม่มีค่าใช้จ่ายเพิ่ม เหมาะกับการทำ Prototype ของนักศึกษาที่มีเวลา/ทรัพยากรจำกัด

**หมายเหตุ:** ถ้าถามต่อว่าทำไมเลือกรุ่น *Flash* ไม่ใช่ *Pro* — สไลด์ไม่ได้ระบุไว้ตรงๆ ควรเตรียมคำตอบเองจากประสบการณ์จริง เช่น งานสร้างข้อมูลตาม pattern/JSON ไม่ต้องใช้ reasoning ขั้นสูงเท่า Pro รุ่น Flash เร็วกว่าและประหยัด Token กว่า เหมาะกับงานที่เรียกซ้ำบ่อย

### 4. ระบบมีบทบาทผู้ใช้งานกี่ระดับ ต่างกันอย่างไร ทำไม Super Admin ต้องขออนุมัติ?

5 บทบาท: QA Tester (ใช้งานหลักสร้าง/ตรวจข้อมูลทดสอบ), Developer (ใช้ข้อมูลทดสอบประกอบพัฒนา/ดีบัก), Business Analyst (กำหนดเงื่อนไขให้ตรงความต้องการธุรกิจ), System Analyst (ตรวจโครงสร้างข้อมูลให้ตรงการออกแบบระบบ), Super Admin (จัดการผู้ใช้งาน อนุมัติคำขอสิทธิ์ ดูสถิติภาพรวมทั้งหมด)

บทบาทอื่นนอกจาก Super Admin เข้าใช้งานได้ทันทีหลังสมัครสมาชิก แต่ Super Admin ต้องได้รับอนุมัติจากผู้ดูแลระบบหลักก่อน เพราะมีสิทธิ์ควบคุมทั้งระบบและผู้ใช้งานคนอื่น หากเปิดให้สมัครแล้วใช้ได้ทันทีจะเสี่ยงต่อการยกระดับสิทธิ์โดยไม่ได้รับอนุญาต

### 5. ระบบมีมาตรการความปลอดภัยอะไรบ้าง?

- เข้ารหัสรหัสผ่านด้วย **SHA-256 + Salt เฉพาะบัญชี** ไม่เก็บรหัสผ่านต้นฉบับไว้เลย
- **Session timeout 10 นาที** เมื่อไม่มีการใช้งาน
- ป้องกันเดารหัสผ่าน: ผิดติดกัน 3 ครั้ง ล็อกบัญชีชั่วคราว 60 วินาที พร้อมแจ้งเตือนทางอีเมล
- จำกัดสิทธิ์ตามบทบาท (Role-based access) — Super Admin ต้องอนุมัติก่อน
- จำกัดข้อมูลที่ส่งไปให้ AI ประมวลผล ให้ส่งเฉพาะเงื่อนไข/โครงสร้าง/คอลัมน์ที่จำเป็นเท่านั้น (ไม่ส่งข้อมูลอ่อนไหวเกินความจำเป็น)

### 6. ทำไมไม่เชื่อมต่อฐานข้อมูลจริงของผู้ใช้งานโดยตรง (เขียนลง DB จริงเลย)?

เป็นการตัดสินใจตั้งแต่ขั้นกำหนดขอบเขต เพื่อความปลอดภัย — ถ้าระบบเขียนเข้าฐานข้อมูลจริงของผู้ใช้โดยตรง ความเสี่ยงจากข้อมูลผิดพลาด/AI มั่วจะกระทบระบบจริงทันที แทนที่จะทำแบบนั้น ระบบส่งออกผลลัพธ์เป็นไฟล์ (.sql/.csv/.json) หรือคำสั่ง SQL ให้ผู้ใช้งานตรวจสอบและนำไปรันเองอย่างควบคุมได้

### 7. บั๊กสำคัญที่เจอระหว่างพัฒนามีอะไรบ้าง แก้ยังไง?

| ปัญหา | สาเหตุ | วิธีแก้ |
|---|---|---|
| Gemini API ไม่ตอบสนอง (HTTP 503) | เรียกใช้โมเดลเวอร์ชันที่ยังไม่เสถียรและมีผู้ใช้งานหนาแน่น | ปรับกลไก Retry (สูงสุด 6 ครั้ง) และกำหนดเวอร์ชันโมเดลที่เสถียรแทน |
| ข้อมูลอ้างอิงบางรายการไม่ถูกใช้ครบ | วิธีสุ่มเลือกข้อมูลแบบเดิมมีโอกาสข้ามบางรายการไป | เปลี่ยนอัลกอริทึมเป็น Fisher-Yates Shuffle + Round-robin แทนการสุ่มของ AI |

บทเรียนที่ได้: ระบบที่พึ่งพา AI ต้องมีชั้นตรวจสอบด้วยโค้ดเสมอ ไม่ควรเชื่อผลลัพธ์จาก AI ทั้งหมด, ความสอดคล้องของชื่อคีย์ระหว่าง Frontend-Backend สำคัญมาก (บั๊กหลายจุดเกิดจากชื่อคีย์ไม่ตรงกัน เช่น structureScript กับ ddlScript), การตรวจ Log จริงช่วยหาจุดบกพร่องได้แม่นยำกว่าการไล่อ่านโค้ดอย่างเดียว, และ Edge Case ต้องคิดตั้งแต่ขั้นออกแบบ ไม่ใช่แก้ทีหลัง

## กลุ่ม B: คำถามทั่วไปตามลำดับหัวข้อสไลด์

### บทนำ / ที่มา / ขอบเขต

**Q: ทำไมถึงเลือกทำหัวข้อนี้ / ปัญหาที่แท้จริงคืออะไร?**
งานทดสอบซอฟต์แวร์และฐานข้อมูลต้องใช้ Test Data จำนวนมากและหลากหลาย การสร้างด้วยมือใช้เวลานาน มักไม่ครอบคลุมทุกเงื่อนไขทางธุรกิจ (เพราะ Human Error จากการสร้างข้อมูลมากเกินไป) และรักษาความสัมพันธ์ระหว่างตาราง (เช่น รหัสพนักงานที่ต้องอ้างอิงกันได้จริง) ได้ยากเมื่อทำด้วยมือ

**Q: ขอบเขตของงานนี้ครอบคลุมและไม่ครอบคลุมอะไรบ้าง?**
ครอบคลุม: เว็บแอปใช้ผ่านเบราว์เซอร์, Google Sheets เป็นฐานข้อมูลหลัก, Gemini API เป็นเครื่องมือสร้างข้อมูล, ส่งออกเป็น SQL ใช้งานต่อได้ทันที ไม่ครอบคลุม: ไม่เขียนเข้าฐานข้อมูลจริงของผู้ใช้โดยตรง, ไม่จัดการโครงสร้างข้อมูลระดับ Enterprise-scale, ไม่ได้พัฒนาโมเดล AI เอง (ใช้บริการ Gemini API)

### เทคโนโลยีและสถาปัตยกรรม

**Q: สถาปัตยกรรมระบบเป็นแบบไหน ทำงานร่วมกันยังไง?**
ผู้ใช้งานเปิดเว็บแอป (โฮสต์บน GitHub Pages) → ส่งคำขอไปยังระบบหลังบ้าน (Google Apps Script) → ระบบหลังบ้านเรียก Gemini API ให้สร้างข้อมูลตามเงื่อนไข → รับกลับมาตรวจสอบคุณภาพ → อ่าน/บันทึกกับ Google Sheets → ส่งข้อมูลที่ผ่านการตรวจสอบแล้วกลับไปแสดงผลบนหน้าเว็บ

**Q: ทำไมใช้ Google Apps Script เป็น Backend ไม่ใช่ Node.js/Python ทั่วไป?**
เพราะทั้งระบบใช้ภาษาเดียวคือ JavaScript ตั้งแต่ Frontend ถึง Backend ไม่มีขั้นตอน Build และเชื่อมต่อ Google Account, Sheets, Gemini ได้โดยตรงแบบ Serverless ไม่ต้องเช่า/ดูแลเซิร์ฟเวอร์เอง เหมาะกับการพัฒนา Prototype ที่มีเวลาและทรัพยากรจำกัด

**Q: ทำไมใช้ Google Sheets เป็นฐานข้อมูลหลัก ไม่ใช้ MySQL/PostgreSQL?**
เพราะเป็นงานระดับ Prototype ของนักศึกษา Sheets เชื่อมต่อกับ Apps Script และ Gemini ได้ทันทีโดยไม่ต้องตั้ง Infrastructure เอง อยู่ในขอบเขตที่กำหนดไว้ตั้งแต่ต้น ข้อจำกัดเรื่องขนาด/ความเร็วเมื่อข้อมูลมากคือสิ่งที่ระบุไว้แล้วใน Limitations และมีแผนจะเชื่อมต่อฐานข้อมูลเชิงสัมพันธ์จริงในอนาคต

### ฟีเจอร์และกลไกการทำงาน

**Q: AI รับผิดชอบส่วนไหน โค้ดควบคุมส่วนไหน?**
AI (Gemini) รับผิดชอบ: ตีความเงื่อนไข/บริบทภาษาธรรมชาติ, สร้างเนื้อหาข้อมูลให้ตรงตาม Business ที่ต้องการ, ประเมินคุณภาพข้อมูลเบื้องต้นด้วยตนเอง (Self-check)
โค้ดของระบบควบคุม (Rule-based): บังคับโครงสร้างคอลัมน์ให้ตรงตาม DDL ทุกครั้งหลัง AI ตอบกลับ, เลือกค่าจากข้อมูลอ้างอิงด้วย Fisher-Yates Shuffle + Round-robin แทนให้ AI สุ่มเอง, คำนวณคะแนนคุณภาพขั้นสุดท้ายและตัดสิน Threshold, จัดเรียงลำดับคอลัมน์ผลลัพธ์
**สรุปสั้นๆ ที่ใช้ตอบได้ทุกคำถามแนวนี้:** "ระบบไม่ปล่อยให้ AI ตัดสินใจเองทั้งหมด แต่ใช้ AI เป็นส่วนหนึ่งของระบบที่มีโค้ดคอยตรวจสอบผลลัพธ์อีกชั้น"

**Q: Reference Column Lock คืออะไร แก้ปัญหาอะไร?**
เป็นฟีเจอร์ที่อ้างอิงค่าจริงจากชุดข้อมูลที่เคยบันทึกไว้ก่อนหน้า เพื่อรักษาความสัมพันธ์และความต่อเนื่องของข้อมูลระหว่างตาราง (เช่น รหัสพนักงานที่มีอยู่จริงในระบบ) แทนที่จะให้ AI สุ่มสร้างค่าขึ้นใหม่ซึ่งอาจไม่ตรงกับข้อมูลเดิม

**Q: ถ้า AI ตอบโครงสร้างข้อมูลผิดจาก DDL จะเกิดอะไรขึ้น?**
โค้ดของระบบจะตรวจสอบและตัดคอลัมน์ที่ไม่ตรงตามที่กำหนดทิ้งทุกครั้งหลัง AI ตอบกลับ ไม่พึ่งพาความแม่นยำของ AI เพียงอย่างเดียว

### สาธิตการใช้งาน

**Q: ตัวอย่างที่สาธิตมายืนยันได้อย่างไรว่าระบบทำงานถูกต้องจริง?**
มีตัวอย่างเปรียบเทียบ "สิ่งที่กำหนด" (DDL Script + เงื่อนไข) กับ "ผลลัพธ์ที่ระบบสร้างจริง" ตรวจสอบ 4 จุด: จำนวน/ชื่อคอลัมน์ตรงตาม DDL ครบทุกรายการ, ลำดับคอลัมน์ตรงตามที่ระบุไม่สลับตำแหน่ง, ค่าข้อมูลตรงตามเงื่อนไข/บริบท, ค่าที่อ้างอิงจากชุดข้อมูลเดิม (Reference Lock) ถูกต้องและครบถ้วน

### การพัฒนาและทดสอบ

**Q: ทดสอบระบบด้านไหนบ้าง?**
5 ด้าน: (1) การสร้างข้อมูลครอบคลุมประเภทข้อมูล จำนวนแถว และ Database Dialect หลากหลาย (2) Reference Column Lock ใช้ข้อมูลอ้างอิงครบทุกรายการไม่ตกหล่น (3) การใช้งานพร้อมกันหลายคน ผ่าน Lock Service กันข้อมูลชนกัน (4) เส้นทางข้อผิดพลาด จำลองกรณี Gemini API ไม่ตอบสนอง (5) ความปลอดภัย ตรวจสอบการยืนยันตัวตน การล็อกบัญชี และสิทธิ์ตามบทบาท ก่อนขึ้นเวอร์ชันจริงต้องผ่าน: ตรวจ Syntax → Diff เทียบผลก่อน-หลังแก้ → ทดสอบระบบจริง → ยืนยันผลจากการใช้งานจริง

**Q: ทำไมใช้ Iterative Development ไม่ใช้ Waterfall?**
เพราะพัฒนาทีละฟีเจอร์แล้วทดสอบบนระบบจริงทันทีก่อนขึ้นเวอร์ชันถัดไป ลดความเสี่ยงจากการออกแบบผิดพลาดตั้งแต่ต้นแล้วมารู้ตัวตอนท้ายแบบ Waterfall ซึ่งเหมาะกับงานที่มีเวลาจำกัดแบบสหกิจ 14 สัปดาห์

### ผลลัพธ์ ข้อจำกัด และสรุป

**Q: ข้อจำกัดของระบบตอนนี้คืออะไร แล้วจะพัฒนาต่อยังไง?**
- Google Sheets จำกัดขนาด/ความเร็วเมื่อข้อมูลมาก → แผน: เชื่อมต่อฐานข้อมูลเชิงสัมพันธ์จริง (MySQL/PostgreSQL)
- พึ่งพา Gemini API เพียงตัวเดียว มีข้อจำกัดโควตา (Retry สูงสุด 6 ครั้ง) — Rule-Based Mode ช่วยลดผลกระทบนี้ได้บางส่วน → แผน: รองรับ AI Model อื่นเป็นทางเลือกสำรอง
- จำกัด 300 แถวต่อคำขอ เพื่อป้องกันคำตอบ AI ถูกตัดก่อนครบ Token → แผน: แบ่งคำขอเป็นชุดย่อยอัตโนมัติ (Batching)
- ยังไม่มี Automated Test Suite ครอบคลุมทั้งระบบ → แผน: พัฒนาเพิ่มเพื่อความมั่นใจระยะยาว

**Q: ถ้าให้สรุปโครงงานนี้ใน 1-2 ประโยค จะพูดว่าอย่างไร?**
"Intelligent Test Data Simulator เป็นเว็บแอปพลิเคชันที่นำ AI มาช่วยแก้ปัญหาการเตรียมข้อมูลทดสอบที่เดิมต้องใช้เวลาและแรงงานมากหากทำด้วยมือ โดยสร้างข้อมูลตามโครงสร้างและเงื่อนไขที่ผู้ใช้กำหนดได้อย่างแม่นยำ พร้อมตรวจสอบคุณภาพข้อมูลและรักษาความสัมพันธ์ระหว่างตารางโดยอัตโนมัติ รวมถึง Rule-Based Mode ที่ช่วยประหยัดการใช้ Token AI"

## จุดที่สไลด์ไม่ได้ให้คำตอบตรงๆ — ควรเตรียมคำตอบเอง

- **ทำไมเลือกเกณฑ์ 70% / 90% พอดี ไม่ใช่ตัวเลขอื่น** — สไลด์ไม่ได้ระบุที่มา ควรตอบจากประสบการณ์จริงว่าปรับค่าระหว่างพัฒนาจนได้ระดับที่กรองข้อมูลคุณภาพต่ำออกได้จริง โดยไม่กรองข้อมูลที่ใช้ได้ทิ้งไปมากเกินไป
- **ทำไมเลือก Gemini Flash ไม่ใช่ Pro** — สไลด์บอกแค่เหตุผลเลือก Gemini โดยรวม ไม่ได้แยกเหตุผลเรื่องรุ่น ควรเตรียมตอบเรื่องความเร็ว/ต้นทุน Token เทียบกับงานที่ไม่ต้องการ reasoning ขั้นสูง
- **ถ้ากรรมการถามให้เดโม่สดหรือลองกรอกเงื่อนไขแปลกๆ** — สไลด์ไม่ครอบคลุมสถานการณ์นี้ ควรลองเทสต์เคสที่ไม่คุ้นก่อนวันสอบ เผื่อกรรมการขอดูสด
